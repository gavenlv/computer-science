## 1. F01 · 循环：让程序替你重复

### 1.1 基本信息

| 项 | 内容 |
| --- | --- |
| 课程 | F01 Python 第一行代码 |
| 模块 | 3 · 条件与循环 |
| 课时 | `F01.control.loops` |
| 时长 | 30 分钟正文 + 30 分钟实验 |
| 先修 | 变量、类型、`if` |

| 难度 | L0 / 2 星 |

### 1.2 学习目标

- **能解释**：为什么需要循环；`for` 和 `while` 分别适合什么场景。
- **能推导**：给定 `range` 和循环体，推出执行次数与最终变量值；能填 trace 表。
- **能实现**：写 `1..100` 求和、偶数筛选、乘法表；能定位并修复死循环。

| --- | --- | --- | --- | --- |
| 0–2 | 问题 | 「老师让你算 1 到 100 的和。你会写 100 行 `print` 吗？程序怎样替你做重复劳动？」 | 一张「100 行代码」 vs 「4 行循环」对比图 | 先不解释语法 |

| 4–8 | 直观模型 | 循环 = 一条传送带：初始化 → 判断 → 执行 → 更新 → 回到判断 | 主视觉「循环执行器」；可单步/播放/重置 | 高亮 `i` 和 `sum` |
| 8–14 | 机制 | `for` 遍历序列；`while` 条件为真；`range(start, stop, step)`；累加器 `sum = sum + i`；trace 表 | 代码 + 变量表同步高亮 | 每步只做一件事 |

### 1.4 主视觉 Spec：循环执行器

**元素**：

- 左侧：代码区（`for` / `while` 两栏可切换）；
- 中间：状态机（初始化 / 判断 / 循环体 / 更新）；
- 右侧：变量表（`i`、`sum`、`n`）与输出区；
- 底部：控制条（上一步/下一步/播放/重置/速度）。

**交互**：

- 单步：高亮当前行，变量表更新；
- 播放：自动执行，速度 0.5x/1x/2x；
- 改参数：`n` 从 10 改到 100，观察步数；
- 制造 bug：关闭 `i += 1`，观察死循环（有安全上限，不会真卡死）。

**教学点**：让「循环」从语法变成「状态在时间上重复变化」。

### 1.5 实验 Spec

**环境**：浏览器 Python（Pyodide）优先；本地 Python 3.11+ 备选。

**初始代码**：

```python
total = 0
for i in range(1, 101):
    total = total + i
print(total)
```

**步骤**：

1. 运行，预期 `5050`；
2. 把 `101` 改成 `100`，观察结果（4950），解释差 100；
3. 打印 1–100 的偶数（两种写法：`if i % 2 == 0` 与 `range(2, 101, 2)`）；
4. 打印 9×9 乘法表；
5. 把求和改成 1..1,000,000，用 `time.perf_counter()` 测时间。

**改一改**：

- 用 `while` 重写求和；
- 求 1..100 的平方和；
- 求偶数和，不能用 `if`（提示：`range` 的 step）。

**弄坏它**：

```python
i = 1
while i <= 100:
    print(i)
    # 故意删掉 i += 1
```

观察现象；用 `Ctrl+C` 停止；解释「条件永远为真」。

**排查**：

- 结果差 1 → 边界包含/不包含；
- 结果每次都是最后一个数 → `sum` 初始化位置错；
- 程序不结束 → 更新语句缺失/条件写错。

### 1.6 检索练习

**Q1** `for i in range(1, 5): print(i)` 输出什么？

- A. 1 2 3 4 5
- B. 1 2 3 4
- C. 0 1 2 3 4
- D. 1 2 3

答案 B。误解：把 `stop` 当成包含。

**Q2** 下面哪段代码能求 1..100 的和？

- A. `sum = 0; for i in range(1,100): sum += i`
- B. `sum = 0; for i in range(1,101): sum += i`
- C. `sum = 1; for i in range(1,101): sum += i`
- D. `for i in range(1,101): sum += i`

答案 B。误解：边界/初始化。

**Q3** 这段代码为什么停不下来？

```python
i = 0
while i < 10:
    print(i)
```

答案：`i` 没有更新。误解：`while` 会自动递增。

**Q4** 填表：`total=0; for i in range(1,4): total += i`，第 2 轮后 `total` 是多少？

答案 3（1+2）。误解：把轮次和值混淆。

**Q5（迁移）** 求 1..100 的偶数和，至少写两种写法，并说明哪种更清晰。

答案：`if i % 2 == 0` 或 `range(2,101,2)`；后者少一次判断，但可读性见仁见智。

### 1.7 常见误区

1. **以为** `range(1, 100)` 包含 100；**实际** 不包含；**因为** `range` 是左闭右开。
2. **以为** 循环一定慢；**实际** 循环是 O(n)，比手写 100 行更可维护；**因为** 常数与规模要分开看。
3. **以为** `for` 只能遍历数字；**实际** 可以遍历字符串、列表、字典；**因为** Python 的迭代协议。

### 1.8 来源与生产备注

- 来源：Python 官方教程（`range`/`for`）、CS61A 循环与递归章节。
- 组件：`LoopStepper`（可复用至 `while`、递归、算法课）。
- 资产：1 个主视觉、2 张对比图、1 个沙箱、1 个终端截图。
- 工作量：约 3–4 人天（含试学修订）。
- 验收：5 名零基础用户中 ≥ 4 人能独立写出求和与偶数筛选；≥ 3 人能解释 `range` 边界。

- **能实现/测量**：写行优先 vs 列优先遍历，测量差异；用 `perf stat` 观察 cache-misses。

| 2–4 | 先猜 | 下面两个遍历，哪个更快？A 行优先 / B 列优先 / C 一样 | 选择后显示「行优先通常快数倍」 | 先不解释 |

### 2.4 主视觉 Spec：缓存模拟器

**元素**：

- 左侧：内存地址网格（0x00–0x3F），每 4 个地址一格（16B），标注缓存行；
- 中间：缓存 8 行（有效位、标签、数据）；可切换直接映射/2 路组相联；
- 右侧：访问序列、命中/缺失计数、命中率、AMAT；
- 底部：访问模式按钮（顺序/步长 2/列优先/随机）、单步/播放/重置。

**交互**：

- 点击一个地址：高亮对应缓存行；命中绿色，缺失红色并加载整行；
- 切换访问模式：观察命中率变化；
- 调整缓存大小/相联度：观察命中率；
- 显示「这次读了多少字节，实际用了多少」→ 缓存行利用率。

**教学点**：把「缓存」从名词变成「一次读一整行的搬运策略」。

### 2.5 实验 Spec

**环境**：浏览器缓存模拟器（必做）+ 本地 C 编译器（选做，用于真实测量）。

**C 代码（核心）**：

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 2048

int main(void) {
    static int a[N][N];
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            a[i][j] = i + j;

    clock_t t0 = clock();
    long sum = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            sum += a[i][j];          // 行优先
    clock_t t1 = clock();

    long sum2 = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            sum2 += a[i][j];         // 列优先
    clock_t t2 = clock();

    printf("row: %.3fs sum=%ld\n", (double)(t1-t0)/CLOCKS_PER_SEC, sum);
    printf("col: %.3fs sum=%ld\n", (double)(t2-t1)/CLOCKS_PER_SEC, sum2);
    return 0;
}
```

**步骤**：

1. 编译 `cc -O2 cache.c -o cache`；
2. 运行，记录行/列时间；
3. 把 `N` 改成 1024/4096，观察差异；
4. 用 `perf stat -e cache-misses,cache-references ./cache` 观察；
5. 在模拟器里复现同样的访问模式。

**改一改**：

- 交换循环顺序；
- 用分块（blocking）优化矩阵乘；
- 把 `int` 换成 `long`，观察缓存行能装多少元素。

**弄坏它**：

- 把二维数组按列访问，观察性能退化；
- 多线程同时写相邻变量，观察伪共享（进阶）。

**排查**：

- 行/列差异不明显 → 编译器优化/数据太小；
- `perf` 无权限 → 用模拟器或 `-O0`；
- 时间波动大 → 多次运行取中位数。

### 2.6 检索练习

**Q1** 命中时间 2ns，缺失率 10%，缺失代价 100ns，AMAT 是多少？

答案：2 + 0.1 × 100 = 12ns。误解：把缺失率当命中率。

**Q2** 缓存行 64B，`int` 4B，一行能装多少个 `int`？

答案：16。误解：以为一行只装一个变量。

**Q3** 为什么列优先遍历大矩阵通常更慢？

答案：空间局部性差，每次访问跳到很远的内存，缓存行利用率低。误解：以为 CPU 对行列一视同仁。

**Q4** 命中率从 90% 提升到 99%，性能提升接近 10 倍吗？

答案：不一定；要看缺失代价占比。用 AMAT 算。误解：线性外推。

**Q5（迁移）** 矩阵乘 `C[i][j] += A[i][k] * B[k][j]`，哪个访问模式不友好？怎么改？

答案：`B[k][j]` 在内层按列访问不友好；可交换循环/分块/转置 B。误解：只改编译器选项。

### 2.7 常见误区

1. **以为** 缓存就是「小一点的内存」；**实际** 它是「按行搬运 + 局部性预测」；**因为** 一次读 64B，命中才快。
2. **以为** 命中率 90% 就是快 90%；**实际** 要看缺失代价；**因为** AMAT 是加权和。
3. **以为** 缓存越大越好；**实际** 命中率、访问模式、成本/功耗都要权衡；**因为** 缓存有面积/延迟代价。

### 3.2 学习目标

- **能推导**：画出双方状态迁移；推出 seq/ack 的变化；分析丢包后的行为。

### 3.3 10 块分镜

| --- | --- | --- | --- | --- |
| 0–2 | 问题 | 「你点开网页，0.2 秒内，浏览器和服务器先说了哪三句话？」 | 浏览器/服务器两端 + 时间轴 | 先不出现 SYN |

### 3.4 主视觉 Spec：握手时序 + 状态机

**元素**：

- 左：客户端状态机（CLOSED / SYN-SENT / ESTABLISHED / FIN-WAIT…）；
- 右：服务器状态机（CLOSED / LISTEN / SYN-RECEIVED / ESTABLISHED）；
- 中：时间轴，三个包（SYN / SYN-ACK / ACK），每个包可展开头部字段；
- 下：双方「已知信息」表（我能发？我能收？对方能发？对方能收？）。

**交互**：

- 单步/播放/重置；
- 点击包 → 显示 seq/ack/flags；
- 切换「丢包」：丢 SYN / 丢 SYN-ACK / 丢 ACK，观察重传与状态；
- 切换「两次握手」模拟：服务器提前 ESTABLISHED，客户端未确认 → 重复连接/资源浪费；
- 切换「SYN Flood」：半连接队列增长。

**教学点**：让「三次握手」变成「双方如何确认四个方向的能力」，而不是背三个包名。

### 3.5 实验 Spec

**环境**：浏览器 pcap 回放（必做）+ 本地 Wireshark/tcpdump（选做）。

**命令**：

```bash
# 终端 1：抓包
sudo tcpdump -i any -nn 'tcp[tcpflags] & tcp-syn != 0' -w handshake.pcap

# 终端 2：发起连接
curl -v http://example.com/

# 查看监听队列
ss -lnt

# Wireshark 过滤
tcp.flags.syn == 1
```

**步骤**：

1. 抓一次 HTTP 请求，找到 SYN / SYN-ACK / ACK；
2. 记录 client_isn、server_isn、ack 号；
3. 对照状态机，标出每一步状态；
4. 用 `ss -lnt` 观察 Recv-Q/Send-Q；
5. 在回放中模拟丢 SYN-ACK，观察客户端重传。

**改一改**：

- 用 `curl --http1.1` vs `--http2` 观察连接复用；
- 访问 HTTPS，观察 TCP 握手后紧跟 TLS 握手；
- 用 `nc -l` 起一个监听，手动发 SYN（进阶）。

**弄坏它**：

- 用防火墙丢弃 SYN-ACK，观察客户端超时/重传；
- 用脚本发起大量半连接，观察 `ss` 队列（仅在本地隔离环境）。

**排查**：

- 抓不到包 → 权限/网卡/过滤条件；
- 看不到三次 → 连接复用/本地回环；
- 时间戳混乱 → 时钟/抓包点。

### 3.6 检索练习

**Q1** 为什么是三次握手，而不是两次？

- A. 三次更安全
- B. 两次无法确认客户端收到了服务器的 SYN-ACK
- C. 三次可以加密
- D. 历史原因

答案 B。误解：把「安全」当原因。

**Q2** 第三次 ACK 丢失，会发生什么？

答案：服务器停留在 SYN-RECEIVED，客户端已 ESTABLISHED；服务器超时重传 SYN-ACK，客户端再 ACK。误解：以为什么都不发生。

**Q3** 客户端 ISN=1000，服务器 ISN=5000。SYN-ACK 的 ack 是多少？

答案：1001。误解：把 ISN 本身当确认号。

**Q4** SYN Flood 攻击的核心资源是什么？

答案：服务器的半连接队列/内存。误解：带宽是唯一资源。

**Q5（迁移）** QUIC 的 0-RTT 如何减少握手？代价是什么？

答案：复用之前的密钥/参数，首包即可带数据；代价是重放风险。误解：0-RTT 等于无握手。

### 3.7 常见误区

1. **以为** 三次握手是为了加密；**实际** 加密是 TLS 的事；**因为** TCP 只负责可靠字节流。
2. **以为** seq 从 0 开始；**实际** 随机 ISN，降低旧连接混淆/攻击；**因为** 序列号空间与安全。
3. **以为** 握手成功就一定可靠；**实际** 只建立连接状态，可靠性靠后续确认/重传；**因为** 网络仍会丢包。
