# 05 · 单课内容标准

> 这一份文档决定「一节课到底长什么样」。
> 目标不是「内容多」，而是让一个高中生能看懂第一遍、大学生能做出第二遍、研究生能读出第三遍。
>
> 每个课时都必须满足本文的 **MUST** 项；SHOULD 项按课程类型取舍。

---

## 1. 一堂好课的定义

### 1.1 三个层次的目标

每节课都要写清三个层次，不能只写「了解/掌握」：

| 层次 | 学习者能做什么 | 验收方式 |
| --- | --- | --- |
| **能解释** | 用自己的话讲清「它解决什么问题、为什么这样设计」 | 口述/短答/给外行讲 |
| **能推导** | 能跟着逻辑推出关键结论，或画出状态/结构 | 推导题/画图/填表 |
| **能实现** | 能写最小实现，或改一个真实系统并验证 | 代码实验/调试挑战 |

如果一节课只有「能解释」，它适合 L0；如果要求「能实现」，必须有可运行实验。

### 1.2 五步探究循环（5E）

| 步骤 | 目的 | 典型形式 |
| --- | --- | --- |
| **Engage 引入** | 制造问题/冲突/好奇 | 真实故障、反直觉现象、历史故事 |
| **Explore 探索** | 先让学习者猜/试/玩 | 交互模拟、预测、手动执行 |
| **Explain 解释** | 给出机制与形式化 | 分步图、状态机、公式、伪代码 |
| **Elaborate 迁移** | 用到新场景/真实系统 | 抓包、源码、性能实验、工程案例 |
| **Evaluate 评估** | 验证是否真的会 | 检索练习、调试题、项目里程碑 |

> 关键顺序：**先探索，后解释**。不要一上来给定义，再举例证明定义。

### 1.3 一节课的「一个主角」原则

- 一节课只允许一个**新核心概念**；
- 允许有多个 supporting details，但必须围绕主角；
- 如果出现两个以上「需要单独一节课才能讲清」的概念，拆分；
- 标题必须体现主角，例如「TCP 如何做到可靠传输」而不是「TCP 概述」。

## 2. 单课结构（10 个块）

标准课时 25–40 分钟正文 + 30–60 分钟练习，总投入约 1–1.5 小时。
建议 8–12 个学习块，每块 2–6 分钟。

| # | 块 | 内容 | 时长 | MUST |
| --- | --- | --- | --- | --- |
| 1 | **本课问题** | 一个真实场景/故障/反直觉现象，引出「为什么需要这个」 | 1–2 min | ✅ |
| 2 | **先猜一猜** | 一个可交互的预测题，不要求正确 | 1–2 min | ✅ |
| 3 | **直观模型** | 一张主视觉/动画，建立心智模型 | 2–4 min | ✅ |
| 4 | **拆解机制** | 分步讲解，每步配图；讲清输入/状态/输出 | 6–10 min | ✅ |
| 5 | **形式化** | 定义、公式、伪代码、状态表（按需） | 3–6 min | ✅（概念课） |
| 6 | **动手实验** | 可运行代码/抓包/SQL/终端，改参数看结果 | 10–20 min | ✅ |
| 7 | **失败案例** | 一个 bug/攻击/性能退化，展示「不懂会怎样」 | 2–4 min | ✅ |
| 8 | **常见误区** | 3 个最容易错的理解，逐条纠正 | 2–3 min | ✅ |
| 9 | **检索练习** | 3–5 题，覆盖回忆/应用/迁移 | 5–10 min | ✅ |
| 10 | **连接与延伸** | 连接上一课/下一课/真实系统/论文 | 1–2 min | ✅ |

### 2.1 每块的具体写法

**块 1：本课问题**

- 用第二人称，写一个具体场景：「你打开一个网页，0.2 秒内发生了什么？」
- 必须包含「不知道这个，会怎样」的代价；
- 不要用「本章将介绍……」的说明书语气。

**块 2：先猜一猜**

- 2–4 个选项，每个选项对应一种常见误解；
- 选择后不立即判对错，先展示「选择分布 + 为什么有人这样想」；
- 让学习者带着悬念进入正文。

**块 3：直观模型**

- 一张图/动画，能用一句话概括；
- 图里最多 7 个元素（工作记忆限制）；
- 配一个「读图任务」：「注意看数据包在哪个节点被拆分」。

**块 4：拆解机制**

- 按「输入 → 状态变化 → 输出」分步；
- 每步只做一件事，配一张局部图；
- 用「如果……会怎样」推进，而不是平铺直叙；
- 关键步骤要有「暂停/继续」或「单步」。

**块 5：形式化**

- 先给直觉，再给符号；
- 每个符号首次出现必须解释；
- 公式配一个「代入具体数字」的例子；
- 伪代码不超过 20 行，必须能跑。

**块 6：动手实验**

- 提供完整可运行代码/命令，不要求安装复杂环境；
- 有「预期输出」，让学习者对照；
- 有 2–3 个「改一改」任务（改参数、改输入、制造错误）；
- 有「如果失败」的排查提示。

**块 7：失败案例**

- 真实事故/漏洞/性能数据，优先于虚构例子；
- 说明「哪个理解错了会导致这个失败」；
- 不要只展示「错误代码」，要展示「错误的心智模型」。

**块 8：常见误区**

- 3 条，格式：「很多人以为……；实际上……；因为……」
- 每条配一个反例/实验；
- 误区要来自真实学习者，而不是凭空编造。

**块 9：检索练习**

- 3–5 题，难度递增：回忆 → 应用 → 迁移；
- 每题有解析，解析里链接回对应块；
- 错题进入复习队列，不要求立刻重做。

**块 10：连接与延伸**

- 「上一课」：一句话回顾；
- 「下一课」：一句话悬念；
- 「真实系统」：一个可验证的链接/命令/源码位置；
- 「延伸」：1 篇论文/1 个开源项目/1 个标准文档（不要列 10 个）。

## 3. 写作规范

### 3.1 语气

- 用「你」和「我们」，像一位耐心的工程师在旁白；
- 允许口语，但不油腻；不写「小白」「保姆级」「一文搞懂」；
- 不居高临下，也不过度卖萌；
- 技术判断要明确：「这里通常选 A，因为……；如果……则选 B」。

### 3.2 类比的使用

- 每个核心概念最多一个主类比，且要标注「类比的边界」；
- 类比必须能推进理解，而不是装饰：
  - ✅ 「TCP 像寄快递：每个包裹有编号，收件人要按编号拼装，丢了要重寄。」
  - ❌ 「TCP 就像一位可靠的朋友。」
- 讲完类比后，必须回到真实机制，指出「哪里不像」。

### 3.3 术语

- 首次出现：中文名（英文名，缩写）+ 一句话解释 + 一张图/例子；
- 之后可以只用缩写，但要有 tooltip/术语表链接；
- 不堆砌术语；一段话最多 2 个新术语；
- 关键术语在页面右侧「术语卡」中可查。

### 3.4 数学

- 先讲「要解决什么问题」，再给符号；
- 公式必须配「读法」和「代入例子」；
- 不要求学习者手算复杂积分/行列式；重点是解释与编程验证；
- 证明只讲套路：构造、反证、归纳、归约。

### 3.5 代码

- 代码块必须可复制、可运行；
- 标明语言、文件路径、依赖；
- 关键行有注释，但不要每行都注释；
- 错误示例要能复现错误；
- 代码长度：教学片段 ≤ 30 行；完整实验 ≤ 200 行；超出则拆文件。

### 3.6 长度

| 课程类型 | 正文字数（中文） | 图/动画 | 交互 | 代码 |
| --- | ---: | ---: | ---: | ---: |
| 概念课（L0–L1） | 1,200–2,000 | 2–4 | 1–2 | 0–1 段 |
| 机制课（L2） | 2,000–3,500 | 3–6 | 1–2 | 1–3 段 |
| 系统/实现课（L3–L4） | 2,500–4,500 | 3–6 | 1–2 | 2–5 段 |
| 论文/研究课（L5） | 2,000–4,000 | 2–4 | 0–1 | 1–2 段 |

> 字数不是目标。超过 4,500 字通常意味着该拆课，而不是「内容更丰富」。

## 4. 视觉规范

### 4.1 图必须承担解释任务

每张图发布前问三个问题：

1. 这张图回答了哪个「为什么/怎么发生」？
2. 去掉这张图，学习者会损失什么理解？
3. 图里有没有无关的装饰元素？

如果答不出 1 或 2，删掉。

### 4.2 视觉类型库

| 类型 | 用来解释 | 示例 | 交互 |
| --- | --- | --- | --- |
| 结构图 | 系统由什么组成 | CPU 数据通路、K8s 架构 | hover 高亮 |
| 流程图 | 步骤/决策 | 编译流程、请求处理 | 单步 |
| 时序图 | 多方交互顺序 | TCP 握手、Raft 选举 | 播放/暂停 |
| 状态机 | 状态与迁移 | TCP 状态、进程状态 | 点击事件 |
| 内存图 | 地址/布局/指针 | 栈帧、堆、页表 | 拖动指针 |
| 数据流图 | 数据怎样变形 | MapReduce、查询计划 | 高亮路径 |
| 几何图 | 空间/变换 | 矩阵变换、相机投影 | 拖拽旋转 |
| 性能曲线 | 参数与结果 | cwnd/RTT、缓存命中率 | 调参 |
| 真实截图/录屏 | 工具与系统 | Wireshark、htop、gdb | 标注 |

### 4.3 图的规范

- **标题**：一句话说明「这张图在讲什么」；
- **图注**：补充「怎么看」，不是重复标题；
- **读图任务**：至少一个「注意看……」的提示；
- **Alt 文本**：为无障碍提供完整描述；
- **来源**：引用真实数据/论文/截图时标注来源与许可；
- **颜色语义**：全站统一（如请求=蓝、响应=绿、错误=红、地址=灰），不能只靠红绿区分；
- **对比度**：正文 ≥ 4.5:1，大字 ≥ 3:1；
- **动画**：默认 2–6 秒循环，提供暂停/单步/速度；尊重 `prefers-reduced-motion`；
- **移动端**：图可纵向重排，不依赖 hover；关键信息不放在图边缘。

### 4.4 动画规范

- 动画只用于「状态随时间变化」或「空间关系变化」；
- 不要用动画做「入场特效」；
- 每个动画必须有静态首帧/末帧，保证可截图理解；
- 单步模式是 MUST：学习者要能停下来观察；
- 动画中的文字要大，至少 16px（移动端 14px 以上）。

### 4.5 真实系统截图

- 优先使用真实终端/抓包/监控截图，而不是重绘；
- 截图必须标注「看哪里」，用箭头/高亮框；
- 敏感信息打码；
- 提供可复现命令，让学习者自己跑一遍。

## 5. 交互规范

### 5.1 交互的四种认知作用

| 作用 | 例子 | 学习目标 |
| --- | --- | --- |
| **预测** | 猜一猜丢包后会发生什么 | 暴露前概念 |
| **操纵** | 拖动 cwnd 滑块，看吞吐变化 | 建立因果 |
| **单步** | 单步执行 TCP 状态机 | 理解顺序 |
| **构造** | 拖拽组件搭一个网络 | 理解组合 |

### 5.2 交互模式库

| 模式 | 适用 | 设计要求 |
| --- | --- | --- |
| 预测-揭晓 | 反直觉概念 | 先记录选择，再解释为什么错 |
| 参数滑块 | 性能/算法/模型 | 显示参数值 + 结果 + 对比基线 |
| 单步执行 | 状态机/解释器/协议 | 高亮当前行/状态，显示变量 |
| 拖拽构造 | 网络/架构/数据包 | 有正确性检查与提示 |
| 沙箱 | 代码/SQL/终端 | 预置环境，一键运行，错误可读 |
| 分支情景 | 安全/架构/故障 | 选择后有后果与复盘 |
| 对比切换 | 算法/架构/参数 | 同一视图切换，保留对照 |
| 调试挑战 | 编程/系统 | 给坏代码/坏配置，让学习者修 |

### 5.3 交互的 MUST

- 有明确的学习目标（不是「好玩」）；
- 有初始状态、操作提示、结果反馈；
- 有「重置」；
- 有「为什么」的解释，不只显示结果；
- 键盘可操作；
- 移动端可用；
- 失败/错误状态有友好提示；
- 不依赖后端也能跑（优先浏览器内）。

### 5.4 交互的反模式

- 点一下放烟花，但没解释；
- 滑块只改变动画速度，不改变语义；
- 交互结果随机，无法复现；
- 需要安装 10 个依赖才能跑；
- 只在桌面端可用；
- 用交互替代讲解，学习者玩完仍不知道原理。

## 6. 实验与代码规范

### 6.1 实验的三种规模

| 规模 | 时长 | 形式 | 例子 |
| --- | --- | --- | --- |
| 微实验 | 2–5 min | 浏览器内代码/命令 | 改一个排序比较函数 |
| 模块 Lab | 30–90 min | 本地/容器 | 实现哈希表、抓包分析 |
| 项目 | 4–20 h | 仓库/部署 | mini OS、RAG 系统 |

### 6.2 实验模板

每个实验必须包含：

1. **目标**：一句话，可验证；
2. **环境**：浏览器/本地/容器，依赖版本；
3. **初始代码/数据**：可运行，不是伪代码；
4. **步骤**：3–7 步，每步有预期输出；
5. **改一改**：2–3 个变式，改变一个变量；
6. **弄坏它**：一个故意失败的实验；
7. **排查**：常见错误与解决；
8. **提交物**：代码/截图/报告；
9. **Rubric**：怎么算完成。

### 6.3 代码运行环境

- **浏览器内**：Pyodide（Python）、WebAssembly（C/C++ 子集）、sql.js（SQL）、JS/TS 原生；
- **容器**：Linux/网络/数据库/OS 实验，提供一键镜像；
- **本地**：需要真实性能/内核/GPU 的实验，提供脚本与版本锁定；
- **远程**：GPU/大模型实验，提供配额与排队（后期）。

### 6.4 可复现性

- 固定依赖版本（lockfile/镜像 digest）；
- 固定随机种子；
- 提供预期输出/基准数据；
- 记录硬件/系统信息（性能实验）；
- 实验结果允许合理误差，给出范围。

## 7. 测评规范

### 7.1 掌握式学习

- 模块测验 ≥ 80 分算掌握；
- 未掌握 → 推送补课/变式题，而不是直接解锁下一模块；
- 允许 2 次尝试，取最高分；第二次题目变体；
- 阶段考试可闭卷 + 开卷 + 项目答辩组合。

### 7.2 题型库

| 题型 | 测什么 | 示例 |
| --- | --- | --- |
| 概念选择 | 回忆/辨析 | 「为什么三次握手不是两次？」 |
| 预测输出 | 理解执行 | 给一段代码/协议事件，预测结果 |
| 找 bug | 调试 | 给一个失败案例，定位原因 |
| 排序/连线 | 顺序/关系 | 排列 TCP 状态迁移 |
| 画图/填图 | 结构 | 补全页表/协议头 |
| 计算 | 应用 | 算 AMAT、RTT、容量 |
| 代码 | 实现 | 实现一个函数/修复一个 bug |
| 短答 | 解释 | 「用 100 字解释为什么缓存有效」 |
| 设计 | 迁移/取舍 | 设计一个短链系统 |
| 论文题 | 研究 | 评价一篇论文的实验设计 |

### 7.3 题目质量

- 每个错误选项都要对应一个真实误解，并在解析中说明；
- 不考「抠字眼」，考「因果/取舍/边界」；
- 计算题给真实数量级，不搞人为复杂；
- 代码题给测试用例，不要求「和标准答案一字不差」；
- 设计题给 Rubric，不搞「参考答案唯一」。

### 7.4 间隔复习

- 首次学习后：1 天、3 天、7 天、21 天复习；
- 复习内容：错题 + 核心概念 + 一个变式；
- 复习失败 → 降级到更基础的知识点；
- 仪表盘显示「今天要复习的 5 张卡」，而不是无限题库。

### 7.5 项目 Rubric（通用）

| 维度 | 1 分（不合格） | 2 分（及格） | 3 分（良好） | 4 分（优秀） |
| --- | --- | --- | --- | --- |
| 正确性 | 跑不起来/结果错 | 基本功能可用 | 边界处理正确 | 有测试/形式化验证 |
| 理解深度 | 只会调库 | 能解释关键流程 | 能解释取舍与原理 | 能改进/对比/证明 |
| 工程质量 | 无结构 | 能读能跑 | 模块化/测试/文档 | 可维护/可观测/可扩展 |
| 性能/可靠性 | 未考虑 | 有基本指标 | 有压测/故障分析 | 有优化/容错/复盘 |
| 表达 | 讲不清 | 能讲流程 | 能讲取舍 | 能讲局限与下一步 |

> 项目通过线：平均 ≥ 3 分，且「正确性」≥ 3 分。

## 8. 项目线规范

| 项目线 | 目标 | 最小交付 | 加分项 |
| --- | --- | --- | --- |
| P0 微作品 | 建立「我能做出来」的信心 | 可运行 + 1 页说明 | 有交互/可视化 |
| P1 入门作品 | 展示结构与测试 | 代码 + README + 测试 | CI/部署 |
| P2 核心 Lab | 证明系统理解 | 可运行 + 测试 + 设计文档 | 性能对比/扩展 |
| P3 方向项目 | 对标经典实现 | 复现 + 报告 + 对比 | 改进/开源 |

## 11. 两个 Storyboard 示例

### 11.1 网络课：TCP 三次握手（L2，35 分钟）

**目标**：能解释为什么需要三次握手、两次为什么不够、握手期间双方状态如何变化；
能在 Wireshark 中认出握手包；能解释 SYN Flood 与半连接队列。

| 时间 | 块 | 内容 |
| --- | --- | --- |
| 0–2 | 问题 | 「你点开网页，0.2 秒内，浏览器和服务器先说了哪三句话？」 |
| 2–4 | 先猜 | 「如果只握手两次，会发生什么？」4 个选项（含「服务器会一直等」「可能建立重复连接」等） |
| 4–8 | 主视觉 | 两个状态机并排，SYN/SYN-ACK/ACK 三个包依次飞过；可单步 |
| 8–14 | 机制 | 每步展开：seq/ack 如何选、为什么随机、半连接队列、状态迁移 |
| 14–18 | 形式化 | 状态迁移表 + 报文头字段图 |
| 18–25 | 实验 | Wireshark 抓包：过滤器 `tcp.flags.syn==1`，对照状态机；改初始序列号观察 |
| 25–28 | 失败案例 | SYN Flood：半连接队列被打满；看 `ss -lnt` 的 Recv-Q/Send-Q |
| 28–31 | 误区 | ①「三次握手是为了加密」②「seq 从 0 开始」③「握手成功就一定可靠」 |
| 31–34 | 练习 | 3 题：预测丢包、解释两次不够、分析一个抓包 |
| 34–35 | 连接 | 下一课「四次挥手」；真实系统：`/proc/net/tcp`；延伸：QUIC 的 0-RTT |

**视觉**：状态机 + 时序图 + 真实抓包截图。
**交互**：点击每个包，显示字段与状态变化；可切换「丢包」情景。
**实验**：浏览器内 pcap 回放 + 本地 Wireshark 二选一。

### 11.2 系统课：指针到底是什么（L1–L2，30 分钟）

**目标**：能解释「变量、地址、值」三者的关系；能读懂 `int *p = &a; *p = 5;`；
能解释段错误与野指针；能在 gdb 中查看地址。

| 时间 | 块 | 内容 |
| --- | --- | --- |
| 0–2 | 问题 | 「为什么改一个函数里的变量，外面的值没变？」 |
| 2–4 | 先猜 | 「`swap(a, b)` 为什么没交换？」选择后展示内存图 |
| 4–9 | 主视觉 | 内存网格：每格有地址、值；变量是「名字→地址」的标签；指针是「值为地址的格子」 |
| 9–15 | 机制 | `&` 取地址、`*` 解引用、指针类型、指针运算、数组退化 |
| 15–18 | 形式化 | 地址/值/类型三元组；`p + 1` 的字节偏移 |
| 18–24 | 实验 | 浏览器内 C 沙箱：打印地址、改 `*p`、制造野指针；gdb `p &a`、`x/4xw` |
| 24–27 | 失败案例 | 段错误/悬垂指针/越界；ASan 报错截图 |
| 27–29 | 误区 | ①「指针就是地址」不完整（还有类型）②「数组就是指针」③「malloc 后自动为 0」 |
| 29–30 | 练习/连接 | 3 题；下一课「结构体与内存布局」；真实系统：`/proc/self/maps` |

**视觉**：可拖拽的内存网格；指针箭头随变量变化。
**交互**：拖动指针到不同地址，观察解引用结果；切换 32/64 位。
**实验**：C 沙箱 + gdb 命令清单。

### 11.3 AI 课：梯度下降为什么有效（L1–L2，30 分钟）

- **问题**：模型怎样「自己变好」？
- **先猜**：学习率太大会怎样？太小会怎样？
- **主视觉**：损失曲面 + 小球下降，可调学习率/动量。
- **机制**：梯度方向、步长、局部极小、鞍点。
- **形式化**：\(w_{t+1} = w_t - \eta \nabla L(w_t)\)。
- **实验**：一维/二维损失函数，调参观察发散/震荡/收敛。
- **失败案例**：学习率过大导致 loss 爆炸；特征未归一化导致震荡。
- **误区**：①「梯度下降一定找到全局最优」②「学习率越小越好」③「loss 下降就代表模型变好」。
- **连接**：下一课「反向传播」；真实系统：PyTorch optimizer。

## 12. 反模式清单

| 反模式 | 为什么有害 | 替代 |
| --- | --- | --- |
| 术语先行 | 学习者不知道为什么要学 | 先问题/现象，再术语 |
| 配图装饰 | 增加认知负荷，不帮助理解 | 图必须回答一个「为什么」 |
| 交互玩具 | 玩完没学到 | 交互必须改变理解，配解释 |
| 只有正确路径 | 不会调试 | 加入失败案例与「弄坏它」 |
| 测验只考记忆 | 高分低能 | 加入预测/找 bug/设计题 |
| 长文/长视频 | 完课率低 | 拆成 8–12 个块，每块 2–6 分钟 |
| 一次讲完 | 记不住 | 间隔复习 + 多阶回访 |
| 虚假「专家级」 | 破坏信任 | 用能力证据与论文/项目定义 |
| AI 生成不审校 | 事实错误/代码跑不通 | 人类审校 + 代码执行 + 来源 |
| 只讲工具 | 工具过时 | 讲原理 + 一个代表实现 |
| 无来源 | 无法核验 | 论文/标准/源码/官方文档 |
| 移动端不可用 | 排除大量学习者 | 响应式 + 键盘 + 图重排 |
