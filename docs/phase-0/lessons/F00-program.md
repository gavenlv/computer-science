## 1. 本课问题：CPU 懂 Python 吗？

你写下：

```python
print("hello")
```

运行，屏幕上出现 `hello`。

但 CPU 并不懂 Python，也不懂「print」，更不懂「hello」。
它只懂一种东西：**指令**（instruction），本质是一串二进制位。

这一课只解决一个问题：

> **一行人类可读的代码，怎样变成 CPU 能执行的指令？中间经历了哪些层？**

学完这一课，你应该能：

- 解释源代码、字节码、机器码的区别；
- 说出编译器和解释器各自做什么；
- 描述 CPU 的「取指 → 译码 → 执行」循环；
- 用 `dis` / `gcc -S` 看到代码「下面一层」；
- 理解「程序也是数据」的存储程序思想。

## 2. 先猜一猜

CPU 最终执行的是什么？

- A. Python 源代码
- B. Python 字节码
- C. 机器指令（二进制）
- D. HTML

<details>
<summary>答案与为什么</summary>

**C. 机器指令。**

CPU 只执行它自己的指令集（x86/ARM/RISC-V 等）对应的机器码。
Python 源代码/字节码都要经过解释器/虚拟机，最终落到机器指令（或由解释器自身的机器码完成）。

B 是中间层：CPython 会先把 `.py` 编译成字节码（`.pyc`），再由解释器循环执行。
但 CPU 不直接执行 Python 字节码。
</details>

## 3. 直观模型：一条流水线

```mermaid
flowchart LR
    A["源代码<br/>hello.py"] --> B["编译/解释<br/>Python/编译器"]
    B --> C["字节码/汇编<br/>中间层"]
    C --> D["机器码<br/>0/1 指令"]
    D --> E["CPU<br/>取指/译码/执行"]
    E --> F["结果<br/>屏幕/文件/网络"]
```

可以把它想成「翻译」：

- 你写的是中文（源代码）；
- 翻译官把它变成英文（字节码/汇编）；
- 最后变成机器能懂的摩斯电码（机器码）；
- CPU 按电码执行。

每一层都存在，是为了让人类好写、让机器好执行。

## 4. 拆解机制

### 4.1 源代码：人类可读的文本

```python
def add(a, b):
    return a + b
```

这是**文本**，不是指令。CPU 不能直接读。

源代码要先被「翻译」：

- **编译器**：一次性翻译成机器码/目标文件；
- **解释器**：逐行/逐段读取、翻译、执行；
- **混合**：先编译成字节码，再由虚拟机解释/JIT 编译。

### 4.2 Python 的路径：源码 → 字节码 → 解释执行

CPython（最常见的 Python 实现）大致是：

```
hello.py → 编译成 bytecode → Python 虚拟机逐条执行 bytecode
```

字节码不是机器码，它是「Python 虚拟机」的指令。

看一个例子：

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
```

你可能会看到类似：

```text
  2           0 RESUME                   0
  3           2 LOAD_FAST                0 (a)
              4 LOAD_FAST                1 (b)
              6 BINARY_OP                0 (+)
             10 RETURN_VALUE
```

不同 Python 版本输出会不同，但意思一样：

- `LOAD_FAST`：把局部变量 `a` 压栈；
- `LOAD_FAST`：把 `b` 压栈；
- `BINARY_OP`：做加法；
- `RETURN_VALUE`：返回结果。

> Python 不是「纯解释、不编译」；它先编译成字节码，再解释执行。
> PyPy 等实现还会做 JIT（运行时编译成机器码）。

### 4.3 C 的路径：源码 → 汇编 → 机器码

C 更接近机器：

```c
int add(int a, int b) {
    return a + b;
}
```

编译：

```bash
cc -S -O0 add.c -o add.s
```

可能得到（x86-64，示意）：

```asm
add:
    movl    %edi, %eax
    addl    %esi, %eax
    ret
```

- `movl`：把第一个参数放到 `eax`；
- `addl`：加第二个参数；
- `ret`：返回。

汇编再被汇编器变成机器码（二进制），链接器把它拼成可执行文件。

### 4.4 CPU 的指令周期

CPU 反复做三件事：

```
取指（Fetch） → 译码（Decode） → 执行（Execute）
```

1. **取指**：根据程序计数器（PC）从内存取一条指令；
2. **译码**：解释这条指令要做什么（加、跳转、读内存……）；
3. **执行**：ALU/寄存器/内存完成操作，PC 指向下一条。

现代 CPU 还会流水线、乱序、分支预测，但基本循环不变。

### 4.5 程序也是数据：存储程序

在冯·诺依曼架构里：

- 指令和数据都放在内存；
- CPU 把「指令」当数据取出来，再译码执行；
- 所以程序可以加载、修改、生成。

这就是为什么：

- 你可以下载一个程序并运行；
- 编译器可以生成机器码；
- 操作系统可以把程序加载进内存、创建进程。

### 4.6 操作系统：把程序变成进程

你双击一个程序：

1. OS 找到可执行文件；
2. 创建进程，分配内存；
3. 把代码/数据加载进地址空间；
4. 设置 PC，开始执行；
5. 进程结束，回收资源。

所以「程序」是磁盘上的文件，「进程」是运行中的实例。

## 5. 形式化：三层表示

| 层 | 例子 | 谁读得懂 | 特点 |
| --- | --- | --- | --- |
| 源代码 | `a + b` | 人 | 可读、可维护 |
| 中间表示 | 字节码/汇编 | 虚拟机/汇编器 | 跨平台/接近机器 |
| 机器码 | `10001011...` | CPU | 快、不可读 |

**抽象**：

```
高级语言 → 中间表示 → 机器码 → 电路
```

每一层都隐藏下一层的细节。你写 `a + b`，不需要知道 ALU 的门电路。

**代价**：

- 抽象层越多，性能开销可能越大；
- 解释执行比机器码慢，但更灵活/跨平台；
- JIT 试图兼顾两者。

## 6. 动手实验：看代码的「下一层」

### 环境

本地 Python 3.11+；可选 C 编译器（`cc`/`gcc`/`clang`）。

### 实验 1：看 Python 字节码

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
```

**任务**：

- 找到 `LOAD_FAST`、`BINARY_OP`、`RETURN_VALUE`；
- 猜每条指令在做什么；
- 把 `a + b` 改成 `a * b`，再看字节码变化。

### 实验 2：看 CPython 的编译缓存

```bash
python -c "import py_compile; py_compile.compile('hello.py')"
ls __pycache__
```

**观察**：`.pyc` 文件里是字节码，不是机器码。
Python 下次会优先加载 `.pyc`（如果源码没变）。

### 实验 3：看 C 汇编（可选）

```c
// add.c
int add(int a, int b) {
    return a + b;
}
```

```bash
cc -S -O0 add.c -o add.s
cat add.s
```

**任务**：找到 `mov`/`add`/`ret`，对照 CPU 指令周期。

### 实验 4：故意制造三种错误

```python
# 语法错误：运行前就会被发现
print("hello"
```

```python
# 运行时错误：运行到才报错
print(1 / 0)
```

```python
# 逻辑错误：不报错，但结果不对
print(1 + 1 * 2)   # 以为 4，实际 3
```

**观察**：三种错误发生在不同阶段。

### 改一改

1. 用 `dis.dis` 看一个 `for` 循环的字节码；
2. 用 `python -m dis file.py` 看整个文件的字节码；
3. 把 C 代码用 `-O2` 编译，观察汇编变化；
4. 查你 CPU 的指令集（x86-64/ARM64）。

### 弄坏它

- 把 `.pyc` 删掉，观察 Python 重新编译；
- 把源码改一行但不删 `.pyc`，观察 Python 是否重新编译（看时间戳）；
- 用 `-O` 运行 Python，观察 `assert` 是否被去掉。

### 排查

| 现象 | 可能原因 |
| --- | --- |
| `dis` 输出看不懂 | 正常；先认 `LOAD_/STORE_/BINARY_/RETURN_` |
| `cc` 找不到 | 没装编译器；用在线编译器/跳过 |
| `.pyc` 不生成 | 权限/`PYTHONDONTWRITEBYTECODE` |
| 汇编和书上不一样 | CPU 架构/编译器/优化级别不同 |

## 7. 失败案例：三个「程序是什么」的误解

### 事故 1：以为 CPU 懂 Python

有人问：「CPU 怎么知道 `print` 是打印？」
答案是：CPU 不知道。`print` 是 Python 解释器提供的一个函数，
最终由解释器调用操作系统/标准库完成输出。

### 事故 2：以为 Python 不编译

Python 会先把源码编译成字节码；只是它不生成独立的机器码可执行文件。
「解释型语言」不等于「没有编译步骤」。

### 事故 3：以为程序就是文件

文件是「静态的代码/数据」；程序运行起来是「进程」，有内存、寄存器、状态。
同一个程序可以同时跑多个进程。

---

## 8. 三个常见误区

1. **以为** CPU 直接执行源代码；
   **实际** CPU 执行机器指令，源代码要经过编译/解释；
   **因为** CPU 只认自己的指令集。

2. **以为** 解释型语言完全不编译；
   **实际** 通常会先编译成字节码/中间表示；
   **因为** 直接解释源码太慢/难优化。

3. **以为** 程序就是磁盘上的文件；
   **实际** 运行中的程序是进程，有独立内存和状态；
   **因为** OS 负责加载、分配资源、调度。

## 9. 检索练习

### Q1

CPU 最终执行什么？

- A. Python 源码
- B. 字节码
- C. 机器指令
- D. 汇编文本

<details>
<summary>答案</summary>

**C. 机器指令。**
汇编文本还要经过汇编器变成机器码；字节码由虚拟机解释。
</details>

### Q2

编译器和解释器的主要区别？

<details>
<summary>答案</summary>

编译器一次性把源码翻译成目标代码（机器码/字节码），再运行；
解释器逐段翻译并执行。很多语言是混合的（先编译字节码，再解释/JIT）。
</details>

### Q3

`dis.dis(add)` 看到的是什么？

<details>
<summary>答案</summary>

Python 字节码（Python 虚拟机的指令），不是 CPU 机器码。
</details>

### Q4

为什么语法错误在运行前就能发现？

<details>
<summary>答案</summary>

因为源码要先被解析/编译；语法不合法，编译阶段就失败，程序还没开始执行。
</details>

### Q5（迁移）

「程序也是数据」是什么意思？为什么重要？

<details>
<summary>答案</summary>

在存储程序架构里，指令和数据都放在内存，CPU 像读数据一样取指令。
所以程序可以加载、修改、生成；换程序不用换硬件，计算机因此通用。
</details>

## 11. 图与交互 Spec（给可视化工程师）

### 主视觉：`ProgramPipeline`

**布局**：

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ 源码      │ 编译/解释 │ 字节码/汇编│ 机器码    │ CPU      │
│ a + b    │ →        │ LOAD_FAST │ 100010... │ 取指/译码 │
└──────────┴──────────┴──────────┴──────────┴──────────┘
```

**交互**：

- 输入一个简单表达式/函数，切换 Python/C；
- 单步「编译」：源码 → 字节码/汇编 → 机器码；
- 点击一条字节码/指令，显示解释；
- 切换 CPU 架构（x86/ARM），看机器码不同；
- 展示「程序 → 进程」的加载过程。

**教学点**：让「代码不是魔法，而是一层层翻译」可见。

### 辅助图

1. 编译 vs 解释；
2. CPU 指令周期；
3. 冯·诺依曼架构；
4. Python 字节码示例。

### 无障碍

- 字节码/汇编有文字解释；
- 可复制代码；
- 颜色不唯一依赖；
- 单步可键盘。
