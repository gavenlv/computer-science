## 1. 本课问题：CPU 那么快，为什么电脑没有快 300 倍？

CPU 做一次加法，大约只要 **0.3 纳秒**（3GHz 的一个时钟周期）。
从内存读一个数，大约要 **100 纳秒**。

如果 CPU 每次都直接等内存，理论上会慢 **300 倍**。
但你的电脑没有慢 300 倍。为什么？

因为 CPU 和内存之间，有几层「更小但更快」的存储：

```
寄存器 → L1 缓存 → L2 缓存 → L3 缓存 → 内存 → SSD
  更快、更小、更贵  ←──────────────→  更慢、更大、更便宜
```

这一课只解决一个问题：

> **缓存凭什么能加速？为什么有的程序快，有的程序慢，哪怕它们做的加法次数一样？**

学完这一课，你应该能：

- 用「局部性 + 缓存行」解释缓存为什么有效；
- 用命中率和缺失代价计算 AMAT；
- 写出行优先/列优先遍历，测出真实差异；
- 解释矩阵乘、图像处理里常见的「访问顺序」优化。

## 2. 先猜一猜

下面两个遍历，都是把 2048×2048 的二维数组所有元素加一遍。
哪个通常更快？

```c
// A：行优先
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += a[i][j];

// B：列优先
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];
```

- A. 行优先
- B. 列优先
- C. 一样快，编译器会优化
- D. 取决于 CPU 型号，没有规律

先选一个，再往下看。

<details>
<summary>答案与为什么</summary>

**A。行优先通常快数倍。**

C 语言的二维数组按**行优先**存储：

```
a[0][0], a[0][1], a[0][2], ... 连续存放
a[1][0], a[1][1], ...
```

行优先遍历访问的是连续内存，一次读入的 64B 缓存行里 16 个 `int` 都能用上。
列优先遍历每次跳到下一行，地址间隔 2048×4 = 8KB，几乎每次都是新的缓存行，
缓存行里另外 15 个 `int` 白白浪费。

这不是「CPU 对行有偏爱」，而是**空间局部性**。
</details>

## 3. 直观模型：CPU 每次搬一整行

### 3.1 存储金字塔

| 层级 | 容量量级 | 延迟量级 | 谁在用 |
| --- | ---: | ---: | --- |
| 寄存器 | 几百字节 | < 1ns | 当前指令 |
| L1 缓存 | 32–64KB | ~1ns | 热数据 |
| L2 缓存 | 256KB–1MB | 3–10ns | 次热数据 |
| L3 缓存 | 几 MB–几十 MB | 10–40ns | 多核共享 |
| 内存 | GB–TB | 50–100ns | 全量数据 |
| SSD | TB | 50–150µs | 持久化 |
| 网络 | 无限 | 0.5ms–几秒 | 远程数据 |

> 数量级会随硬件变化，但「越近越快越小越贵」的规律不变。

### 3.2 缓存行：一次搬 64 字节

CPU 不是「读一个 `int` 就搬 4 字节」，而是**一次搬一整条缓存行**（通常是 64B）。

64B 能装：

- 16 个 `int`（4B）；
- 8 个 `long`（8B）；
- 1 个很小的结构体；
- 或者……你只用到的 1 个字节，剩下 63B 全浪费。

所以缓存是否有效，取决于：

1. 你访问的数据是否**连续**（空间局部性）；
2. 你访问的数据是否**最近用过**（时间局部性）；
3. 一条缓存行里的数据，是否**都被用上**（缓存行利用率）。

### 3.3 命中与缺失

- **命中（hit）**：要的数据已经在缓存里，直接取；
- **缺失（miss）**：不在，去下一层取，并把整行搬上来。

命中率高，平均访问时间就短；命中率低，CPU 就经常等内存。

## 4. 拆解机制

### 4.1 时间局部性：刚用过的，还会再用

```c
for (int i = 0; i < N; i++) {
    sum += a[i];
    sum += a[i];   // 第二次访问，大概率命中
}
```

同一个地址短时间内被访问两次，第二次就可能命中。

### 4.2 空间局部性：旁边的，可能马上用

```c
for (int i = 0; i < N; i++) {
    sum += a[i];   // 访问 a[i] 时，a[i+1..i+15] 也被搬进缓存
}
```

下一次访问 `a[i+1]`，大概率命中。这就是为什么「顺序访问」比「跳跃访问」快。

### 4.3 缓存行利用率

假设缓存行 64B，`int` 4B：

- 顺序访问：一行 16 个 `int` 都用上，利用率 100%；
- 每隔 16 个 `int` 访问一次：一行只用 1 个，利用率 6.25%；
- 列优先遍历 2048 列：每次跳到 8KB 外，一行只用 1 个，利用率极低。

### 4.4 映射与替换

缓存很小，内存很大，所以需要一个「地址 → 缓存行」的映射：

- **直接映射**：每个内存块只能放到一个固定位置，简单但容易冲突；
- **组相联**：每个块可以放到一组里的任意位置，冲突少一些；
- **全相联**：随便放，最灵活但最贵。

当缓存满了，要替换掉一行。常见策略：

- **LRU**：替换最久没用的；
- **Clock**：LRU 的近似，硬件友好；
- **随机**：简单，效果不一定差。

### 4.5 写策略

- **写回（write-back）**：先写缓存，等替换时再写内存，快；
- **写直达（write-through）**：每次写都写内存，简单但慢。

> 本课不要求你设计缓存，只要理解「为什么访问顺序会影响性能」。

## 5. 形式化：AMAT

**平均内存访问时间**（AMAT, Average Memory Access Time）：

```
AMAT = 命中时间 + 缺失率 × 缺失代价
```

例子：

- 命中时间：2ns；
- 缺失率：10%；
- 缺失代价：100ns。

```
AMAT = 2 + 0.10 × 100 = 12ns
```

如果命中率从 90% 提升到 99%：

```
AMAT = 2 + 0.01 × 100 = 3ns
```

从 12ns 降到 3ns，约 **4 倍**，不是 10 倍。
这就是为什么「命中率提高 9 个百分点」不等于「性能提高 10 倍」。

### 5.1 缓存行能装多少元素

```
一行元素数 = 缓存行大小 / 元素大小
```

- 64B / 4B = 16 个 `int`；
- 64B / 8B = 8 个 `long`；
- 64B / 1B = 64 个 `char`。

### 5.2 为什么矩阵乘要「分块」

矩阵乘 `C[i][j] += A[i][k] * B[k][j]` 的内层循环如果按 `k` 访问 `B[k][j]`，
每次都会跳到 `B` 的下一行，空间局部性差。

常见优化：

- 交换循环顺序（`i-k-j`），让 `B` 的访问更连续；
- 转置 `B`；
- 分块（blocking），把大矩阵切成能放进缓存的小块。

### 实验 2：真实 C 测量

```c
#include <stdio.h>
#include <time.h>

#define N 2048
static int a[N][N];

int main(void) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            a[i][j] = i + j;

    clock_t t0 = clock();
    long long sum = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            sum += a[i][j];          // 行优先
    clock_t t1 = clock();

    long long sum2 = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            sum2 += a[i][j];         // 列优先
    clock_t t2 = clock();

    printf("row: %.3fs sum=%lld\n", (double)(t1 - t0) / CLOCKS_PER_SEC, sum);
    printf("col: %.3fs sum=%lld\n", (double)(t2 - t1) / CLOCKS_PER_SEC, sum2);
    return 0;
}
```

编译运行：

```bash
cc -O2 cache.c -o cache
./cache
```

**预期**：行优先明显快于列优先（常见 2–10 倍，取决于 CPU/缓存大小）。
如果差异很小，检查：

- `N` 是否太小（数据全在 L3 里）；
- 编译器是否把循环优化掉了；
- 是否在虚拟机/容器里有额外开销。

### 实验 3：看 cache-misses（可选）

```bash
perf stat -e cache-misses,cache-references ./cache
```

**预期**：列优先的 `cache-misses` 明显更高。
如果没有权限，用 `sudo` 或跳过此步，用模拟器代替。

### 改一改

1. 把 `N` 改成 512 / 1024 / 4096，观察差异变化；
2. 把 `int` 改成 `long`，一行能装几个？
3. 交换矩阵乘的循环顺序，测时间；
4. 用分块（blocking）优化矩阵乘。

### 弄坏它

- 把二维数组按列访问，观察性能退化；
- 让多个线程同时写相邻变量，观察伪共享（进阶）；
- 把缓存模拟器的行大小改成 16B，观察命中率变化。

### 排查

| 现象 | 可能原因 |
| --- | --- |
| 行/列差异不明显 | 数据太小、全在缓存里；编译器优化 |
| `perf` 报权限错误 | 需要 `perf_event_paranoid` 或 `sudo` |
| 时间波动大 | 多次运行取中位数；关闭其他负载 |
| 结果不对 | `sum` 溢出（用 `long long`） |

## 7. 失败案例：列优先遍历慢 5–10 倍

一个真实的图像处理/矩阵计算程序，逻辑完全正确，但比同事的版本慢 5 倍。
最后发现：内层循环按列访问一个大数组。

```c
// 慢：内层按列访问
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];
```

**错误的心智模型**：「循环次数一样，性能就应该一样。」
**实际**：CPU 不是按「次数」访问内存，而是按「缓存行」搬运数据。
访问顺序决定了缓存行利用率，进而决定性能。

---

## 8. 三个常见误区

1. **以为** 缓存就是「小一点的内存」；
   **实际** 它是「按行搬运 + 局部性预测」；
   **因为** 一次读 64B，命中才快。

2. **以为** 命中率 90% 就是快 90%；
   **实际** 要看缺失代价；
   **因为** AMAT 是加权和，不是线性比例。

3. **以为** 缓存越大越好；
   **实际** 命中率、访问模式、成本/功耗都要权衡；
   **因为** 缓存有面积、延迟和功耗代价。

## 9. 检索练习

### Q1

命中时间 2ns，缺失率 10%，缺失代价 100ns，AMAT 是多少？

<details>
<summary>答案</summary>

`2 + 0.1 × 100 = 12ns`。
注意：缺失率是 10%，不是命中率 10%。
</details>

### Q2

缓存行 64B，`int` 4B，一行能装多少个 `int`？

<details>
<summary>答案</summary>

`64 / 4 = 16` 个。
</details>

### Q3

为什么列优先遍历大矩阵通常更慢？

<details>
<summary>答案</summary>

空间局部性差。每次访问跳到很远的内存，缓存行里大部分数据用不上，
缓存行利用率低，缺失率高。
</details>

### Q4

命中率从 90% 提升到 99%，性能会提升接近 10 倍吗？

<details>
<summary>答案</summary>

不一定。用 AMAT 算：

- 90%：2 + 0.1 × 100 = 12ns；
- 99%：2 + 0.01 × 100 = 3ns。

大约 4 倍，不是 10 倍。要看命中时间与缺失代价的占比。
</details>

### Q5（迁移）

矩阵乘 `C[i][j] += A[i][k] * B[k][j]`，哪个访问模式不友好？怎么改？

<details>
<summary>答案</summary>

内层按 `k` 访问 `B[k][j]` 是按列访问，不友好。
可以：

- 交换循环顺序为 `i-k-j`；
- 转置 `B`；
- 分块（blocking）。

目标都是让内层访问连续内存，提高缓存行利用率。
</details>
